## Context discipline

Your context window is limited. Protect it.

1. Name the specific question before opening any file. Never read "to get oriented."
2. Read at most three files per task. If you need more, list them with a reason and stop.
3. Read only the section you need from long files (`.tex`, logs, large scripts).
4. Never open a dataset directly. Write code that prints its dimensions, variable list,
   and summaries, and read that output.
5. Do not read `MEMORY.md` whole. Search it:
   `Select-String -Path MEMORY.md -Pattern "LEARN:<topic>"`.
6. When the PI assigns an exploratory task, propose the reading list first.

If a task needs more than this, it is too broad: say so and ask the PI to split it.

## Mandatory workflow

1. **Plan.** For any non-trivial step, write `quality_reports/plans/plan_<STEP>.md`: the
   estimand, inputs, specification, sensitivity set, and the decision rule fixed *before*
   estimation. Stop for PI approval.
2. **Commit.** `git add -A; git commit -m "checkpoint before <STEP>"`.
3. **Execute.** Implement in `Data_and_Estimation/Code/`, run it, and inspect the actual output.
4. **Report.** Write `quality_reports/report_<STEP>.md` in the format below.
5. **Log.** Append each decision to `quality_reports/decision_log.md`:
   `YYYY-MM-DD | <STEP> | decision | reason | approved by`.
6. **Stop.** Do not begin the next step without explicit PI approval.

If a run fails, make at most two fix attempts, then stop and report the error verbatim.
Never loop.

**Starting a new session.** Read the most recent file in `quality_reports/plans/`, run
`git log --oneline -5` and `git status`, and state in one sentence what you understand the
current task to be. Wait for the PI to confirm.

Do not make unrequested judgment calls about sample restrictions, category mappings, minimum
cell sizes, deflators, outlier treatment, weights, clustering, or model selection. When the
protocol is underspecified, document the gap in the report and stop if it blocks valid
continuation.

## Report format — `quality_reports/report_<STEP>.md`

Use these sections, in this order. Keep chat replies short; detail goes here.

1. **Header** — title; `Status:` (draft / awaiting PI review / approved); `Date:`;
   `Authority:` the PI approval or protocol step that authorises the work.
2. **Result and decision-relevant interpretation** — lead with the estimate and its interval.
   Apply the pre-fixed decision rule. State what the result does and does not establish.
3. **Estimand, data, and implementation** — the exact target quantity and units; code entry
   points as relative links; input files; keys and merges asserted; sample and row counts
   after each restriction; weights, clustering, and inference method; seeds.
4. **Results tables** — every number traceable to a saved file in `Outcomes/`, linked.
5. **Robustness** — the precommitted sensitivity set only. Label any extra check *post hoc*.
6. **Verification ledger** — what was asserted, what reconciled and to what tolerance,
   which logs finished cleanly, and which checks could not be completed and why.
7. **Strongest supported statement** — one paragraph, labelled descriptive, associational,
   causal, or structural.
8. **Gate** — "Stop here for PI review," and what was deliberately not started.

## Rules

1. Never write to `Data_and_Estimation/Data/Raw_Data/`.
2. Execute every script before reporting that it works. Quote failures verbatim.
3. Do not invent functions, arguments, or options. Verify against the installed version.
4. Preserve random seeds and state them in the report.
5. Every table and figure is produced by code. Never edit an exhibit by hand.
6. Do not change a specification to make an error or an unwelcome result go away.
7. Track row counts after every restriction and merge; assert keys; report duplicates,
   unmatched rows on both sides, and thin cells.
8. Do not silently trim, winsorize, impute, smooth, or recode. Flag suspiciously clean results.
9. Never describe a compilation as successful until the PDF exists and all passes finish.

## Claim discipline

- Separate descriptive, associational, causal, and structural claims; label which one applies.
- A wide interval spanning zero means the design cannot distinguish the quantities. It is
  neither support for either hypothesis nor an execution failure.
- Nested, overlapping, or correlated estimates are not independent confirmations.
- Name the binding measurement or identification constraint before tuning secondary choices.
- Do not promote a provisional instrument, estimator, or sample to the main specification
  without PI approval.

## Code conventions

**Scripts** — numbered `NN_verb_object`, one task per script, relative paths, a log written to
`Outcomes/Logs/`, and a final `PASS`/`FAIL` line the report can cite.

**R** — `fixest` for panel estimation; fixed effects after `|`; clustering with
`cluster = ~var` (there is no `clust.var`); pass formula objects, not pasted strings; tables
with `etable()`.

**Julia** — one project environment per repository; commit `Project.toml` and `Manifest.toml`.

**Stata** — forward slashes in paths (a backslash before a macro suppresses expansion);
`capture noisily`, never bare `capture`; tempfiles do not persist between runs; compare
zero-padded string codes via `real()`.

**Figures** — publication-ready: labelled axes and units, white background, saved from code.
